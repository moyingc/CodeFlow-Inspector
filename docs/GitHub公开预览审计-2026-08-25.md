# GitHub 公开预览审计（2026-08-25）

## 结论

当前项目适合以 **Alpha / Research Preview** 形式公开获取反馈，不适合标记为稳定版、生产级安全证明器或已经成熟的全语言分析平台。

“禁止商业使用”与 OSI 开源定义不兼容。若采用非商业许可证，发布说明应使用“源码可见”或 “source-available”，不能称为 Open Source。

## 孪生算法候选

- 算法实验当前从 `speedOptions` 选取收益评分最高的策略，仅输出性能、稳定、资源和适配估计。
- 策略候选没有携带确定性源码编辑，因此不会自动生成候选代码。
- 修复台过去同时把原文写入左右编辑框，视觉上看起来像“候选与原代码一致”。现在策略候选会把建议代码留空，明确等待真实修改。
- Diff 层仍会拒绝原文与替换相同、工作区哈希相同、目标歧义或过期的编辑。

## 孪生与测试边界

可以共享：一次受控运行的退出码、stdout/stderr、CPU、内存、trace、文件改动和隔离证据。

不能混为同一结论：

- 测试验证已声明预期是否满足；孪生比较条件变化后的系统行为。
- 功能/冒烟/集成可消费 baseline 运行，但必须拥有各自断言，不能只凭进程退出 0 同时判定通过。
- 性能/负载可以消费 stress 样本，但负载结论需要规模、并发和持续时间；孪生压力实验还需要容量边界和退化曲线。
- 算法替换只能消费真实候选 Diff 的 A/B 结果；没有代码变化时必须保持“未证明”。

## 发布前仍需决定

1. 选择真正开源许可证，或选择非商业 source-available 许可证并使用准确称呼。
2. 初始化 Git 仓库并确认首批文件清单。
3. 更新 README 的旧“原型/未来建议”内容，改成当前真实能力、限制和最小演示流程。
4. 首次推送后检查 GitHub Actions 的 Linux、Windows、macOS 构建结果。
5. 为公开仓库启用 Private Vulnerability Reporting、Dependabot 和分支保护。

## 同类产品差距

当前差距主要不在页面数量，而在多年积累的语言/框架模型、规则准确率、误报回归语料、大型项目基准、IDE/CI 生态、版本兼容矩阵和安全响应流程。项目的差异化价值是本地优先、面向非专业用户的代码解读、可视数据路径、受控运行证据和候选修复门禁。公开预览应围绕这些差异化能力收集可复现反馈，不应直接与成熟 SAST 产品比“规则总量”。
